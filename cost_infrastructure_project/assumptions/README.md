# assumptions/

## cost_assumptions.csv

This file is the **single source of truth** for every cost figure used in the
infrastructure model. It is deliberately kept as a plain, editable CSV rather
than buried in Python so that:

1. Non-programmers on the team can review/edit it.
2. Every number is traceable to an explicit source, justification, and
   uncertainty range.
3. The code never has to "guess" at a cost — every row has a real numeric
   `cost_usd`, and any row that's missing one is excluded from totals and
   flagged, never silently treated as zero or as a real cost.

**This CSV is reproducible.** Every value in it was generated by
`scripts/generate_cost_assumptions.py`, which documents the exact formula or
scaling rule behind each number. Run `python scripts/generate_cost_assumptions.py --check`
to verify the checked-in file still matches. If you want to change a scaling
assumption, change it in the generator script and re-run — don't hand-edit
numbers you can't trace back to a documented rule (though you're free to
hand-edit the CSV directly for quick experiments; just know the generator
will overwrite it if re-run).

## The two systems

Rather than comparing two real companies, every cost component is modelled
for **two neutral architectural archetypes**:

- **`Search_Oriented_System`** — a crawl/index/serve architecture (the kind
  of system a search engine needs): data acquisition, preprocessing,
  **index build**, compute, storage, query-time serving, engineering, and
  ongoing evaluation/maintenance.
- **`LLM_Oriented_System`** — a train-or-adapt/fine-tune/serve architecture
  (the kind of system an LLM product needs): data acquisition,
  preprocessing, **model training/adaptation**, compute, storage,
  inference serving, engineering, and ongoing evaluation/maintenance.

These are **not** claims about Google's, Sarvam's, or any other specific
company's actual costs — they're transparent scenario models for comparing
two different system *architectures* at the same corpus size. Where a
component genuinely differs between the two (e.g. "build a search index"
vs. "train/adapt a language model"), that difference is captured in the
`indexing_or_training` component; everywhere else the two systems use the
same 8-component schema so the comparison stays apples-to-apples.

## Columns

| column                      | meaning                                                                 |
|------------------------------|--------------------------------------------------------------------------|
| `component`                  | one of the 8 cost components (see below)                                |
| `system`                     | `Search_Oriented_System` or `LLM_Oriented_System`                        |
| `scenario`                   | `SMALL` / `MEDIUM` / `LARGE` (corpus size scenario)                      |
| `cost_type`                  | `one_time` (initial investment) or `recurring_annual`                    |
| `cost_usd`                   | the BASE numeric cost estimate in USD                                    |
| `unit`                       | currency/unit of `cost_usd` (currently always USD)                       |
| `assumption_type`            | see below                                                                 |
| `justification`               | free text explaining the number and its scaling logic                     |
| `source`                      | where the number/formula came from                                        |
| `confidence_or_uncertainty`    | a **± percentage** used for LOW/HIGH sensitivity bounds (see below)        |

## The 8 components

**Initial / one-time:**
`data_acquisition`, `preprocessing_setup`, `indexing_or_training`, `engineering_setup`

**Recurring annual:**
`storage`, `compute`, `serving_inference`, `maintenance_operations`

Every `(system, scenario)` combination is expected to have all 8. The code
checks this explicitly (`infrastructure_model.py:validate_cost_assumptions`)
and flags any combination that's missing one — see "Completeness checking"
below.

## `assumption_type` categories

- **`assignment_input`** — a number that comes directly from the course
  assignment brief (currently only the `data_acquisition` rows, derived from
  the USD 1,000 / 100,000-words rule). These rows have
  `confidence_or_uncertainty = 0` and are **never perturbed** in the
  sensitivity analysis — they're a fixed fact, not a scenario assumption.
- **`formula_derived`** — a number computed from an explicit formula that
  also exists elsewhere in this codebase (currently the
  `LLM_Oriented_System` / `indexing_or_training` rows, derived from the
  Approach B adaptation-cost formula in `src/cost_model.py`).
- **`modelling_assumption`** — a reasonable, explicitly documented scenario
  input chosen for this project (the majority of rows). Clearly **not** a
  real internal company figure — see each row's `justification`.
- **`public_source`** — reserved for a number backed by a real, citable
  external reference. Not currently used by any row; available if you want
  to replace a modelling assumption with a sourced figure later.

## `confidence_or_uncertainty` and sensitivity analysis

This column holds a **± percentage**. The code uses it to compute LOW/HIGH
bounds around the BASE `cost_usd` value:

```
LOW  = cost_usd × (1 − confidence_or_uncertainty / 100)
BASE = cost_usd
HIGH = cost_usd × (1 + confidence_or_uncertainty / 100)
```

For example, `preprocessing_setup` with `cost_usd=35000` and
`confidence_or_uncertainty=30` gives a range of $24,500 (LOW) to $45,500
(HIGH). `assignment_input` rows always show `confidence_or_uncertainty=0`
and are excluded from perturbation entirely (see
`src/infrastructure_model.py:_apply_sensitivity`).

If a row's `confidence_or_uncertainty` is blank or non-numeric, the code
falls back to `config.yaml -> sensitivity.default_uncertainty_pct` (25% by
default) rather than treating it as zero uncertainty.

See `results/final/tables/cost_sensitivity_analysis.csv` and
`results/final/figures/sensitivity_range.png` for the LOW/BASE/HIGH output.

## Completeness checking

Unlike the old placeholder-based system, this schema does not ship with
blank rows. Every row that exists has a real numeric `cost_usd`. The
completeness check instead verifies that **all 8 expected components are
present** for each `(system, scenario)` combination. If you delete a row
(e.g. while experimenting), the corresponding total will:

- exclude that component from the sum (never treat it as zero silently),
- get flagged `is_complete = False` with the missing component named in
  `missing_components`,
- print a validation warning listing exactly which component is missing
  from which `(system, scenario)`.

This is intentionally stricter than "some rows are optional" — if the
schema says 8 components, a complete comparison needs all 8, or the
incompleteness needs to be visible in the output rather than silently
absorbed into the total.

## Components intentionally NOT modelled

Some plausible cost components (marketing/user acquisition, legal/
regulatory compliance, customer support operations) were considered and
deliberately **excluded from the schema entirely** rather than added as
placeholder rows, because no defensible corpus-size-based scaling
assumption could be made for them in a course project. This rationale is
also printed in `integration_summary.txt` under Section 2. If you want to
add a component, add it to `EXPECTED_INITIAL_COMPONENTS` /
`EXPECTED_RECURRING_COMPONENTS` in `src/infrastructure_model.py`, then add
real rows for it (both systems, all 3 scenarios) — don't add a partial or
placeholder row.

## How to edit this file

Two options:

1. **Edit `scripts/generate_cost_assumptions.py`** (recommended) — change
   the scaling logic or formula for a component, then re-run
   `python scripts/generate_cost_assumptions.py` to regenerate the CSV.
   This keeps every number traceable to documented code.
2. **Edit `assumptions/cost_assumptions.csv` directly** — fine for quick
   experiments (Excel, Google Sheets, or a text editor all work since it's
   plain CSV), but note the generator will overwrite your changes if
   someone re-runs it. If you make a manual edit you want to keep, update
   the generator script to match.
